11월 셋째 주에 서버 운영자라면 그냥 넘기기 어려운 취약점 두 묶음이 하루 간격으로 공개됐습니다. 하나는 Java 런타임 자체의 결함인 Java4Shell이고, 다른 하나는 Nginx의 NGINX2Root입니다. 둘 다 조건이 맞으면 로그인 없이 원격에서 코드를 실행할 수 있는 종류라서 정부 기관도 바로 점검과 업데이트를 권고했습니다.

저희도 운영 중인 서버에 대한 조치를 마쳤습니다. 이 글에서는 내부 구성 이야기 대신, 공개된 권고를 기준으로 무엇을 확인하고 어떤 순서로 조치하면 되는지를 정리합니다.

> 2026년 11월 25일 기준으로 공개된 권고와 분석 글을 정리했습니다. 영향 범위와 해결 버전은 이후에 바뀔 수 있으니, 실제 조치 전에는 글 끝의 공식 권고를 다시 확인해 주세요.

## 한눈에 보기

| | Java4Shell | NGINX2Root |
|---|---|---|
| 대표 CVE | CVE-2026-114938 | CVE-2026-123007 외 4건 |
| 공개일 | 11월 17일 | 11월 18일 |
| 대상 | OpenJDK 계열 Java 17, 21, 25, 27 | nginx 오픈소스, NGINX Plus |
| 핵심 조건 | AVX-512 VBMI를 지원하는 x86-64 CPU | HTTP/2 사용 (대표 CVE 기준) |
| 해결 버전 | 17.0.21.1, 21.0.13.1, 25.0.5.1, 27.0.1.1 | 1.30.7(stable), 1.31.9(mainline) 이상 |
| 국내 권고 | 11월 18일 긴급 점검 권고, 20일 보완 | 11월 19일 KISA 보안 업데이트 권고 |

두 건 모두 "버전만 보고는 해당 여부를 알 수 없다"는 공통점이 있습니다. Java는 CPU 조건이 붙고, Nginx는 설정과 배포판 패키지 방식에 따라 판단이 달라집니다.

## 1. Java4Shell (CVE-2026-114938)

### 무엇이 문제인가

JVM(HotSpot)에는 Base64 디코딩을 CPU 명령어로 빠르게 처리하는 가속 루틴이 들어 있습니다. 이 루틴이 형식이 잘못된 마지막 Base64 묶음을 처리할 때 남은 출력 길이를 잘못 계산해서, 정해진 버퍼를 넘어 메모리에 쓰는 일이 생깁니다. Java 코드 쪽에서는 잘못된 입력이라며 예외를 던지지만, 그 시점에는 이미 메모리가 손상된 뒤입니다.

애플리케이션 코드의 버그가 아니라 런타임의 결함이라는 점이 중요합니다. 외부에서 들어온 값을 Base64로 디코딩하는 서비스라면 해당 경로가 있을 수 있고, 인증 헤더처럼 로그인 전에 디코딩하는 값이 대표적인 예로 거론됩니다.

### 영향받는 조건

아래 조건을 **모두** 만족해야 영향을 받습니다.

- Java 17(17.0.6 이상), 21, 25, 27의 수정 전 버전
- x86-64 CPU이면서 AVX-512 VBMI 명령어를 지원
- Base64 가속 기능이 켜져 있음 (CPU가 지원하면 기본으로 켜짐)

영향받지 않는 경우는 다음과 같습니다.

- 일반 Java 8, Java 11 (단, Java 8 Enterprise Performance Pack은 예외로 영향을 받음)
- ARM64 서버, AVX-512 VBMI가 없는 x86-64 서버

### 얼마나 심각한가

Oracle과 OpenJDK는 CVSS 3.1 기준 8.1(High)로 평가했고, 공격 난도는 높다고 봤습니다. 취약점을 찾은 보안 업체는 CVSS 4.0 기준 9.2(Critical)로 매겼습니다. 여러 보안 업체가 테스트 환경에서 인증 없는 코드 실행을 재현했지만, 항상 성공하는 수준은 아니라는 분석도 있습니다. 공개 시점에 실제 공격에 악용됐다는 보고는 없었습니다. 그래도 미국 CISA가 즉시 패치를 촉구했을 만큼, 미뤄 둘 종류는 아닙니다.

### 해결 버전

| 계열 | 해결 버전 |
|---|---|
| Java 17 | 17.0.21.1 |
| Java 21 | 21.0.13.1 |
| Java 25 | 25.0.5.1 |
| Java 27 | 27.0.1.1 |

Temurin, Corretto, Red Hat, Microsoft 빌드처럼 배포판마다 버전 표기가 조금씩 다릅니다. 쓰고 있는 배포판의 보안 공지에서 11월 17일 수정이 들어간 빌드인지 확인하는 것이 정확합니다.

### 해당 여부 확인하기

서버의 CPU가 조건에 해당하는지부터 봅니다. 아무것도 출력되지 않으면 이 취약점의 조건에 해당하지 않습니다.

```bash
grep -m1 -o -w avx512vbmi /proc/cpuinfo
```

다음으로 실제로 돌고 있는 Java를 확인합니다. 터미널에서 `java -version`으로 보이는 Java와 서비스가 쓰는 Java가 다를 수 있으니, 실행 중인 프로세스 기준으로 봐야 합니다.

```bash
# 실행 중인 JVM 목록과 각 프로세스의 런타임 버전
jcmd -l
jcmd <pid> VM.version

# 컨테이너라면 컨테이너 안에서 확인
docker exec <컨테이너> java -version
```

### 조치

1. 배포판의 수정 버전으로 Java를 업데이트합니다.
2. 서비스를 재시작합니다. 파일만 바꾸고 재시작하지 않으면 예전 런타임이 그대로 돕니다.
3. 컨테이너는 베이스 이미지를 새로 받아 이미지를 다시 빌드하고 재배포합니다. 실행 중인 컨테이너는 태그가 갱신돼도 바뀌지 않습니다.
4. 재시작 후 `jcmd <pid> VM.version`으로 해결 버전에서 돌고 있는지 확인합니다.

당장 업데이트가 어렵다면 임시 조치로 Base64 가속만 끄는 JVM 옵션이 안내되어 있습니다. 다른 CPU 최적화는 그대로 두고 문제의 루틴만 우회합니다.

```bash
export JAVA_TOOL_OPTIONS="-XX:-UseBASE64Intrinsics"
```

임시 조치는 어디까지나 업데이트 전까지의 방편입니다. 적용했다면 수정 버전 배포 후에 잊지 않고 걷어내야 합니다.

### 놓치기 쉬운 곳

- **한 서버의 여러 Java**: 패키지로 설치한 것 외에 압축을 풀어 둔 JDK가 따로 있을 수 있습니다.
- **제품에 내장된 Java**: 검색 엔진, CI 서버, 인증 서버처럼 자체 JDK를 포함해 배포되는 제품은 그 제품의 업데이트를 따로 적용해야 합니다.
- **외부 솔루션과 장비**: 납품받은 솔루션이나 장비에 Java가 들어 있으면 공급사에 영향 여부를 확인해야 합니다.

## 2. NGINX2Root (CVE-2026-123007 외)

### 무엇이 문제인가

nginx는 11월 18일에 1.30.7(stable)과 1.31.9(mainline)를 내면서 취약점 10건을 한꺼번에 고쳤습니다. 그중 인증 없이 원격 코드 실행까지 이어질 수 있는 5건을, 발견한 연구팀이 NGINX2Root라고 이름 붙였습니다.

대표는 CVE-2026-123007입니다. HTTP/2의 흐름 제어 값을 계산하는 과정에서 정수 언더플로가 일어나 메모리가 손상됩니다. nginx가 HTTP/2를 처음 지원한 1.9.5(2015년)부터 있던 결함이라, 사실상 HTTP/2를 켠 거의 모든 버전이 대상입니다. nginx 자체 코드의 문제이므로 뒤에 어떤 애플리케이션이 있는지와 무관합니다.

### 5건의 노출 조건

| CVE | 유형 | 노출되는 설정 |
|---|---|---|
| CVE-2026-123007 | 정수 언더플로 | HTTP/2 사용 |
| CVE-2026-123633 | 해제 후 사용 | HTTP/2로 받아 백엔드로 프록시하고, 워커 연결 수가 부족해지는 상황 |
| CVE-2026-123634 | 해제 후 사용 | 변수가 들어간 프록시 대상 이름 + SSI 또는 mirror 하위 요청 |
| CVE-2026-121810 | 해제 후 사용 | HTTP/3 사용 |
| CVE-2026-113425 | 해제 후 사용 | 메일 프록시로 사용 |

HTTP/2를 켠 리버스 프록시 구성이라면 위의 두 건이 직접 해당할 수 있습니다.

### 얼마나 심각한가

F5는 5건 모두 CVSS 4.0 기준 9.2(Critical)로 평가했습니다. 다만 F5의 설명으로는 보통은 워커 프로세스가 죽는 서비스 거부 수준이고, 코드 실행은 메모리 주소 무작위화(ASLR)가 꺼져 있거나 우회된 경우에 가능합니다. 연구팀은 주소를 먼저 알아낸 뒤 명령을 실행하는 데까지 시연했습니다. 11월 23일 기준으로 CISA의 악용 확인 목록(KEV)에는 올라 있지 않습니다.

### 해결 버전

- stable: **1.30.7** 이상
- mainline: **1.31.9** 이상
- 1.29 이하 구버전 계열은 별도 수정판이 없으므로 위 버전으로 올려야 합니다.

닷새 뒤인 11월 23일에는 후속 수정이 하나 더 나왔습니다. `ssl_early_data on`을 쓰는 서버에서 CPU 코어 하나를 계속 점유하게 만들 수 있는 서비스 거부 결함(CVE-2026-132779)으로, **1.30.8**과 **1.31.10**에서 고쳐졌습니다. 지금 올린다면 이 버전을 기준으로 잡는 편이 낫습니다.

### 배포판 패키지는 버전 숫자가 그대로다

Ubuntu나 Debian의 nginx 패키지는 버전을 올리지 않고 보안 수정만 옮겨 넣습니다. 그래서 업데이트한 뒤에도 `nginx -v`는 1.24.0 같은 예전 숫자를 그대로 보여 줍니다. 이 경우에는 nginx 버전이 아니라 **패키지 버전**을 배포판 보안 공지와 비교해야 합니다.

```bash
nginx -v
dpkg -l nginx | tail -1      # 패키지 버전 확인 (Ubuntu·Debian)
```

Ubuntu 24.04는 수정이 두 차례에 나뉘어 나왔다는 분석이 있으니, 한 번 업데이트했더라도 최신 패키지인지 다시 확인하는 것이 좋습니다. 표준 지원이 끝난 Ubuntu 20.04는 무료 저장소에 수정판이 없습니다.

반대로 nginx 공식 Docker 이미지는 배포판 패키지가 아니어서 버전 숫자를 그대로 믿어도 됩니다. 대신 `1.28`처럼 이전 계열 태그를 쓰고 있다면 수정이 들어가지 않으므로 `stable`이나 `1.30` 이상으로 바꿔야 합니다.

### 해당 여부 확인하기

설정에서 HTTP/2를 쓰는지 확인합니다.

```bash
sudo nginx -T 2>/dev/null | grep -n "http2"
```

설정 검색만으로는 놓칠 수 있으니 바깥에서 실제로 접속해 보는 것이 확실합니다. 응답 첫 줄이 `HTTP/2`로 시작하면 HTTP/2가 켜져 있는 것입니다.

```bash
curl -sI --http2 https://도메인 | head -1
```

앞단에 CDN이나 로드밸런서가 있으면 그 장비가 HTTP/2를 대신 받고 있을 수 있습니다. 이때는 nginx가 직접 받는 주소와 포트로 확인해야 합니다.

### 조치

```bash
# Ubuntu·Debian 패키지
sudo apt update
sudo apt install --only-upgrade nginx
sudo systemctl restart nginx

# Docker
docker compose pull
docker compose up -d
```

여기서 가장 흔한 실수가 `reload`로 끝내는 것입니다. reload는 설정만 다시 읽고 실행 파일은 바꾸지 않아서, 패키지를 올려도 예전 프로그램이 계속 돕니다. 반드시 **restart**를 하고, Docker에서는 컨테이너를 새로 만들어야 합니다.

### 임시 조치의 한계

바로 업데이트할 수 없다면 HTTP/2를 끄는 방법이 있습니다. 다만 한계가 분명합니다.

- 5건 중 HTTP/2와 관련된 2건만 막습니다.
- 같은 주소와 포트를 쓰는 모든 `server` 블록에서 꺼야 합니다. 하나라도 남으면 그쪽으로 우회됩니다.
- 클라이언트는 HTTP/1.1로 내려가고, gRPC처럼 HTTP/2가 필수인 서비스는 동작하지 않습니다.

### 컨테이너 밖으로 나가는 경로

연구팀은 nginx 결함에 리눅스 커널의 SCTP 결함을 엮어, 컨테이너 안의 nginx에서 호스트의 root 권한까지 얻는 과정을 설명했습니다. 이 커널 결함은 11월 21일 기준으로 CVE 번호와 패치가 확인되지 않았습니다. nginx를 올리면 진입 지점은 막히지만, "컨테이너 안이라 괜찮다"는 가정은 하지 않는 편이 안전합니다.

## 조치 순서 정리

두 취약점에 공통으로 적용할 수 있는 순서입니다.

1. **목록 만들기**: 서버별로 어떤 Java와 nginx가 어디에서 돌고 있는지 적습니다. 컨테이너와 제품 내장 런타임까지 포함합니다.
2. **조건 확인**: Java는 버전과 CPU, nginx는 버전과 HTTP/2·HTTP/3·메일 프록시 설정을 봅니다.
3. **우선순위**: 인터넷에 공개된 서비스부터 조치합니다.
4. **업데이트**: 수정 버전을 설치하고, 재시작하거나 컨테이너를 다시 배포합니다.
5. **검증**: 설치된 버전이 아니라 실행 중인 프로세스의 버전을 확인합니다.
6. **기록**: 조치한 서버와 일시, 적용 버전을 남기고, 걸어 둔 임시 조치는 해제합니다.

## 정리하며

이번 두 건을 보면서 다시 확인한 점이 있습니다. 하나는 버전 번호만으로는 판단이 끝나지 않는다는 것입니다. 같은 Java 21이어도 CPU에 따라 해당 여부가 갈리고, 같은 nginx 1.24.0이어도 패키지 버전에 따라 수정 여부가 갈립니다. 다른 하나는 "설치"와 "적용"이 다르다는 것입니다. 패키지를 올리는 일과, 실행 중인 프로세스가 새 버전으로 바뀌는 일은 별개이고, 그 사이를 메우는 것이 재시작과 검증입니다.
